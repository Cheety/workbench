# Architekturtests sind eigene Bun-Tests im Paket `@workbench/architecture`

ADR-0002 und ADR-0004 verlangen Architekturtests: Ein Plugin importiert aus einem anderen nur dessen Contract, der Contract hängt nicht vom Server- oder Client-Teil seines Plugins ab, und Core und SDK enthalten außer dem Workspace keine Fachsprache. Die Prüfungen sind eigener Code, der als `bun test` läuft und damit Teil von `bun run check` ist; ein Architekturtest-Werkzeug war freigegeben, wird aber nicht eingesetzt. Erwogen wurde dependency-cruiser: Es kennt keine Plugin-Pakete, die Regeln müssten Paketnamen und Contract-Verzeichnisse als Pfadmuster wiederholen, statt sie wie der Kernel aus `workbench.plugin` und `exports` zu lesen (ADR-0007), und es wäre eine weitere Abhängigkeit mit eigener Konfigurationssprache.

Die Prüfungen liegen in einem eigenen Paket `packages/architecture`, nicht im Core. Erwogen wurde der Core; dann stünde die Liste der Fachbegriffe in dem Code, den sie prüft, und Code, der nie zur Laufzeit läuft, läge im Core.

Ein Plugin-Paket ist wie beim Kernel ein Paket, dessen `package.json` `workbench.plugin` nennt. Sein Contract ist das Verzeichnis der Datei, die `exports["./contract"]` nennt, ohne die Tests darin. Drei Regeln machen dieses Verzeichnis zur Grenze: Die Dateien des Contracts importieren aus ihrem eigenen Paket nur Dateien des Contracts, sonst nur andere Pakete und die Contracts fremder Plugins. Die exportierte Datei erreicht über relative Importe jede Datei des Contracts. Das Verzeichnis enthält nicht den Einstieg des Plugins. Ein Import des Contracts lädt damit nur Dateien dieses Verzeichnisses, und jede Datei darin lädt er mit; Server- oder Client-Code kann weder hinter einem Import des Contracts noch unbemerkt neben ihm liegen. Tests sind ausgenommen, weil kein Import des Contracts sie lädt; deshalb darf auch keine Datei des Contracts einen Test importieren.

Erwogen wurde, das Verzeichnis ohne die Erreichbarkeit als Contract zu nehmen; dann zählte bei `./src/contract.ts` ganz `src/` zum Contract, Client-Code daneben eingeschlossen. Erwogen wurde auch, den Contract als die Dateien zu bestimmen, die der Export über Importe erreicht; dann wäre jede vom Contract importierte Datei selbst Contract, und die Regel könnte nie verletzt sein. Die gewählte Regel verbindet beides: Das Verzeichnis begrenzt, was der Contract importieren darf, die Erreichbarkeit, was im Verzeichnis liegen darf. Bisher war der Contract genau die exportierte Datei, die keine Datei ihres Pakets importieren durfte; das war ebenso dicht, zwang aber jeden Contract in eine einzige Datei. Ebenso erwogen wurden feste Verzeichnisse `server/`, `client/` und `contract/`; das wäre Verdrahtung über Namen statt über eine ausdrückliche Angabe.

Importe findet die Prüfung über die Modulpfade im Quelltext, reine Typ-Importe eingeschlossen. Erwogen wurde `Bun.Transpiler.scanImports`; es lässt Typ-Importe weg, und gerade sie sind zwischen Plugins der häufigste Weg ins Innere eines anderen.

Fachsprache ist eine feste Liste von Begriffen der geplanten fachlichen Plugins und des Referenz-Plugins (etwa `kanban`, `issue tracker`, `note`). Geprüft werden der Core und das SDK; nach ADR-0004 kennt auch das SDK die Fachsprache der Plugins nicht. Die Prüfung zerlegt jede ihrer Dateien in Wörter (Bezeichner, Strings, SQL) und sucht die Begriffe darin; die Liste nennt zu jedem Begriff Einzahl und Mehrzahl (`agent factory`, `agent factories`), weil sich die Mehrzahl nicht verlässlich aus der Einzahl bilden lässt. Tests sind ausgenommen, weil ihre Fixture-Plugins eigene Fachlichkeit haben. `issue` allein steht nicht auf der Liste, weil der Core das Wort für Befunde einer Validierung braucht (`ConfigIssue`, `error.issues` von zod); erfasst wird `issue tracker`.

Core und SDK importieren außerhalb ihrer Tests kein Plugin-Paket, auch nicht dessen Contract; nach ADR-0007 findet der Kernel die Plugin-Pakete erst zur Laufzeit über ihre `package.json`. Die Prüfung nutzt dieselbe Erkennung von Plugin-Paketen und Importen wie die Plugin-Grenzen und erfasst damit Paketname, jeden Subpath, relative Pfade in ein Plugin-Paket und Pfade durch `node_modules`. Tests sind ausgenommen, weil sie ein Plugin-Paket laden dürfen, um den Kernel damit zu prüfen.

Dass eine Event-Definition im Contract liegt (ADR-0015), sichert eine Prüfung am Namen: `defineEvent` steht in einem Plugin-Paket nur in Dateien seines Contracts, wobei die Prüfung das Wort im Quelltext sucht, Kommentare und Strings eingeschlossen, und Tests ausnimmt, weil ihre Fixture-Plugins eigene Events definieren.

## Consequences

- Die Liste der Fachbegriffe ist nie vollständig. Wer ein fachliches Plugin anlegt, trägt dessen Kernbegriffe in `packages/architecture/src/domain-language.ts` ein.
- Die Prüfung sieht nur Modulpfade, die als Literal im Quelltext stehen. Ein berechneter Import entginge ihr; deshalb ist er in Plugin-Paketen außerhalb ihrer Tests selbst ein Verstoß (`computed_import`): `import(…)`, `require(…)`, `require.resolve(…)`, `import.meta.resolve(…)` und `mock.module(…)` nennen ihren Modulpfad dort als einfaches String-Literal, nicht als Variable, Verkettung oder Template-Literal mit `${…}`. Core und SDK sind ausgenommen, weil der Kernel Plugins nach ADR-0007 über einen berechneten Pfad lädt; ein berechneter Import dort entgeht der Prüfung auf Plugin-Importe weiterhin. Ein Text in Kommentar oder String, der wie ein Import aussieht, zählt dagegen mit; im Contract macht er eine Datei auch dann erreichbar, wenn kein Import sie lädt, und in einem Plugin-Paket ist `require(x)` in einem Kommentar ein `computed_import`.
- Ein Contract kann nicht als Bedingungsobjekt (`{ "types": …, "default": … }`) exportiert werden, sondern nennt genau eine Datei.
- Ein Contract darf aus mehreren Dateien bestehen, aber nur aus Dateien seines Verzeichnisses. Nennt `./contract` eine Datei in einem Verzeichnis mit anderem Code, etwa `./src/contract.ts` neben `src/client/`, schlägt die Prüfung fehl; der Contract braucht dann ein eigenes Verzeichnis.
