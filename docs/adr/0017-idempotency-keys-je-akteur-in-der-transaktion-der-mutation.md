# Idempotency-Keys gelten je Akteur und werden in der Transaktion der Mutation beansprucht

Ein Aufrufer, dessen Anfrage an einer Zeitüberschreitung oder Verbindung scheitert, weiß nicht, ob die Mutation festgeschrieben wurde. Wiederholt er sie, darf das keinen zweiten Effekt haben. Er gibt deshalb einen Idempotency-Key mit, und die Pipeline führt die Mutation für denselben Key nur einmal aus und gibt jedem weiteren Aufruf dieselbe Antwort. Ein Plugin tut dafür nichts, wie beim Audit (ADR-0014).

Ein Key gilt je Akteur: Der Schlüssel von `core.idempotency_keys` ist `(actor_kind, actor_id, key)`. Zwei Akteure, die zufällig denselben Key wählen, stören einander nicht, und kein Akteur erfährt etwas über die Aufrufe eines anderen. An den Key gebunden sind Operation, Workspace und Eingabe des ersten Aufrufs; ein weiterer Aufruf mit demselben Key, der eines davon ändert, wird mit `idempotency_key_reused` (Art `rejected`, HTTP 422) abgelehnt, wie es der Entwurf [draft-ietf-httpapi-idempotency-key-header](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) für eine andere Payload vorsieht. Erwogen wurde, den Key je Akteur und Operation zu führen; dann liefe ein Key, den ein Aufrufer versehentlich für zwei Operationen verwendet, still zweimal, statt den Fehler im Aufrufer zu zeigen.

Die Eingabe vergleicht der Core über einen SHA-256-Hash der Eingabe, wie der Aufrufer sie schickte, als JSON mit sortierten Schlüsseln: Dieselben Felder in anderer Reihenfolge sind dieselbe Eingabe. Erwogen wurde, die Eingabe selbst zu speichern und zu vergleichen; sie kann Secrets und personenbezogene Daten enthalten, die das Audit aus demselben Grund nicht speichert. Erwogen wurde auch, die Eingabe nach dem Eingabe-Schema zu vergleichen; dann entschiede eine Änderung des Schemas zwischen zwei Aufrufen, ob sie gleich sind.

Beansprucht wird der Key in der Transaktion der Mutation, bevor `execute` läuft: `INSERT … ON CONFLICT DO NOTHING` legt die Zeile an. Läuft ein zweiter Aufruf mit demselben Key, während der erste noch nicht festgeschrieben ist, wartet Postgres mit dessen Einfügen auf den ersten. Schreibt der erste fest, findet der zweite die Zeile und antwortet mit ihr, ohne `execute`; rollt der erste zurück, legt der zweite die Zeile an und führt die Mutation selbst aus. So führen zwei gleichzeitige Aufrufe nie zweimal aus, und keiner muss es erneut versuchen. Erwogen wurde, wie im Entwurf einen laufenden Aufruf mit 409 abzulehnen; dafür müsste der Key vor der Mutation in einer eigenen Transaktion festgeschrieben werden, und ein Prozess, der danach stirbt, hinterließe einen Key ohne Antwort, den jemand aufräumen müsste. Erwogen wurde eine Advisory Lock auf einen Hash des Keys; ihr Namensraum ist derselbe, den die Migrationen und jedes Plugin mit Datenbank nutzen, und zwei Keys mit demselben Hash warteten aufeinander. Wie lange der zweite wartet, begrenzt das `statement_timeout` der Verbindung (60 s).

Festgehalten wird nur die Antwort einer gelungenen Mutation. Scheitert sie, rollt ihre Transaktion den Key mit zurück, und ein weiterer Aufruf mit ihm führt sie erneut aus. Erwogen wurde, wie manche Zahlungsanbieter auch das Scheitern festzuhalten; das bräuchte eine zweite Transaktion nach dem Zurückrollen mit eigenem Fehlerpfad (ADR-0014 verwirft sie aus demselben Grund), und eine gescheiterte Mutation hat nichts verändert, was eine Wiederholung verdoppeln könnte. Ein Aufrufer, dessen Mutation an einem Zustand scheiterte, der sich inzwischen geändert hat, erhält so die Antwort auf den jetzigen Zustand.

Die Antwort steht als JSON-Text in einer Spalte vom Typ `json`, nicht `jsonb`: `json` bewahrt den Text, wie er geschrieben wurde, samt Reihenfolge der Felder, sodass die Wiederholung dieselben Bytes liefert wie die erste Antwort. Schon die erste Antwort eines Aufrufs mit Key ist die JSON-Form der Ausgabe, damit beide gleich sind, auch im Test-Harness, das keine HTTP-Antwort serialisiert. Die Spalte darf leer sein, weil die Zeile vor `execute` entsteht und die Antwort erst danach in derselben Transaktion bekommt; eine festgeschriebene Zeile hat sie immer, das lässt sich aber nicht als `CHECK` ausdrücken.

Eine Wiederholung schreibt keinen Audit-Eintrag, publiziert kein Event und reiht keinen Job ein: Sie ist kein weiterer Vorgang, nur die Antwort auf den ersten. Eine Query beachtet den Key nicht, weil sie nichts verändert, was eine Wiederholung verdoppeln könnte; so kann ein Aufrufer jeden Aufruf gleich behandeln. Der Key selbst muss aber auch dort 1 bis 255 sichtbare ASCII-Zeichen oder Leerzeichen lang sein, sonst `invalid_idempotency_key` (HTTP 400); das entspricht einem String der Structured Fields (RFC 9651), den der Entwurf für den Header vorsieht. Erwogen wurde, einen Key auf einer Query abzulehnen; dann müsste ein Aufrufer mit allgemeiner Wiederholungslogik jede Operation nach ihrer Art unterscheiden.

## Consequences

- Die Pipeline prüft den Key vor der Eingabe und beansprucht ihn nach der Prüfung des Workspace. Kommt die Rechteprüfung dazu, muss sie vor der Wiederholung liegen, sonst erhielte ein Akteur nach dem Entzug eines Rechts noch die Antwort eines früheren Aufrufs.
- Ein Aufruf, der auf einen laufenden mit demselben Key wartet, hält solange eine Verbindung des Pools.
- Eine Ausgabe, die keine JSON-Form hat (etwa ein `BigInt`), lässt eine Mutation mit Key scheitern (`internal_error`), auch wenn sie ohne Key gelänge.
- `core.idempotency_keys` verweist per Fremdschlüssel auf `core.workspaces`; ein Workspace, auf den ein Key verweist, lässt sich nicht löschen, solange der Key besteht.
