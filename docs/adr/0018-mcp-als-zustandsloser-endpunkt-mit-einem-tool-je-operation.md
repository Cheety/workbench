# MCP ist ein zustandsloser Endpunkt der HTTP-API mit einem Tool je Operation

Jede Operation des Cores und der aktiven Plugins erscheint einem MCP-Client als Tool. Der Endpunkt ist `POST /api/mcp` mit dem Transport Streamable HTTP des [Model Context Protocol](https://modelcontextprotocol.io), zustandslos und mit JSON-Antworten statt eines SSE-Streams: Jede HTTP-Anfrage trägt ihr API-Token, wird wie ein Aufruf der HTTP-API authentifiziert (ADR-0012, ADR-0013) und erhält ihre eigene Korrelations-ID; es gibt keine Session, die der Server über Anfragen hinweg halten, aufräumen und zwischen zwei Prozessen teilen müsste. Weil der Pfad unter `/api/` liegt, antwortet er wie die Operationen mit 503 (`instance_not_ready`), solange die Operationen der Plugins nicht feststehen. `GET` und `DELETE`, mit denen ein Client einen Stream öffnet oder eine Session beendet, beantwortet er vor der Prüfung des Tokens mit 405 und `Allow: POST`, wie es die Spezifikation für einen Server ohne Stream vorsieht. Erwogen wurde der Transport über stdio; er liefe als eigener Prozess auf dem Rechner des Clients, bräuchte dort Zugang zur Datenbank und umginge die Authentifizierung. Erwogen wurde auch, Sessions anzubieten; sie brächten nichts, solange kein Tool Fortschritt meldet oder Rückfragen stellt.

Der Name eines Tools ist der Name der Operation mit `_` statt `.`: `reference.createNote` heißt `reference_createNote`. Die Spezifikation erlaubt den Punkt, verbreitete Modell-APIs aber nicht, deren Funktionsnamen nur Buchstaben, Ziffern, `_` und `-` haben dürfen; ein Client müsste den Namen dann selbst umschreiben, jeder auf seine Weise. Die Abbildung lässt sich umkehren, weil weder ein Plugin-Name (`[a-z][a-z0-9-]*`, ADR-0007) noch der Name einer Operation in camelCase (ADR-0010) einen Unterstrich enthalten kann; der Core nimmt nur die Namen an, die `tools/list` nennt, und gibt der Pipeline die Operation dazu. Einen anderen Namen, auch den einer Operation mit `.`, lehnt er wie die HTTP-API eine unbekannte Operation mit `unknown_operation` ab; sonst riefe ein Name, den kein Client sieht, dieselbe Operation auf.

Die Argumente eines Tools sind `{ "workspace": <UUID>, "input": <Eingabe> }`; das Eingabe-Schema des Tools setzt das JSON Schema der Eingabe der Operation, das auch der OpenAPI-Vertrag nennt, unter `input` ein. Erwogen wurde ein Endpunkt je Workspace (`/api/workspaces/{workspace}/mcp`), dessen Tools die Eingabe der Operation unverändert als Argumente hätten; dann bräuchte ein Agent je Workspace einen eigenen MCP-Server in seiner Konfiguration, und eine Operation, deren Eingabe kein Objekt ist, ließe sich nicht als Tool beschreiben, weil MCP als Argumente nur ein Objekt kennt. Erwogen wurde auch, `workspace` neben die Felder der Eingabe zu stellen; dann verdeckte es ein gleichnamiges Feld einer Operation. Fehlt `workspace` oder ist es keine UUID, scheitert der Aufruf mit `invalid_workspace_id` wie ein ungültiger Pfad der HTTP-API.

Eine Mutation nimmt als drittes Argument `idempotencyKey`, den Idempotency-Key aus ADR-0017; ihr Eingabe-Schema nennt es mit dem Muster des Headers `Idempotency-Key`, das einer Query nicht, wie der OpenAPI-Vertrag den Header nur an Mutationen nennt. Der Key gilt je Akteur, nicht je Weg: Wiederholt ein Agent über MCP einen Aufruf, den er über HTTP mit demselben Key schickte, erhält er dieselbe Antwort. Erwogen wurde, den Key in `_meta` des Aufrufs zu tragen; dort steht er in keinem Schema, und ein Modell, das die Argumente eines Tools aus dessen Schema füllt, erführe nie von ihm. Ist das Argument bei einer Mutation kein String, scheitert der Aufruf mit `invalid_idempotency_key`, wie ein ungültiger Key; eine Query beachtet es wie den Header nicht.

Das Ergebnis eines Tools ist ein Textblock mit der Ausgabe als JSON, mit denselben Feldern und Werten wie der Body der HTTP-API; die Reihenfolge der Felder sagt beiden nichts zu, wie JSON selbst. Scheitert die Operation, ist das Ergebnis ein Tool-Fehler (`isError: true`), dessen Textblock die Problem Details der HTTP-API als JSON trägt, mit demselben `code`. So sieht ein Modell, warum ein Aufruf scheiterte, und kann ihn berichtigen, und ein Programm unterscheidet die Fälle wie über HTTP. Auch eine unbekannte Operation ist ein Tool-Fehler, obwohl die Spezifikation dafür einen Fehler des Protokolls vorschlägt; sonst käme `unknown_operation` über MCP anders als über HTTP. Erwogen wurde, die Ausgabe zusätzlich als `structuredContent` mit dem Ausgabe-Schema als `outputSchema` zu liefern; MCP verlangt dort ein Objekt, die Ausgabe einer Operation muss keines sein, und der Client prüfte das Schema ein zweites Mal mit eigenem Validator.

Eine Query trägt die Annotation `readOnlyHint: true`, eine Mutation `false`; so kann ein Client Queries ohne Rückfrage zulassen. Eine Beschreibung hat ein Tool nicht, weil eine Operation keine hat.

Der Server nennt sich `workbench` in der Version des API-Vertrags, derselben, die `info.version` in `docs/openapi.json` trägt: Beide beschreiben dieselben Operationen und ändern sich zusammen. Erwogen wurde die Version des Paketes `@workbench/core`; sie steht auf `0.0.0` und sagt einem Client nichts.

Der Core nutzt das MCP-SDK (`@modelcontextprotocol/sdk`) für Protokoll und Transport, aber dessen Klasse `Server`, nicht `McpServer`. `McpServer` nimmt die Schemas eines Tools nur als zod-Schemas an, erzeugt das JSON Schema selbst und prüft die Argumente vor dem Aufruf; der Core müsste dafür zod-Typen der Plugins erwarten, was ADR-0010 ausschließt, und die Eingabe würde zweimal geprüft, einmal mit anderen Meldungen als in der Pipeline. `Server` ist im SDK als veraltet markiert, mit dem Hinweis, ihn für solche Fälle weiter zu nutzen. Der Core baut je Anfrage einen `Server` mit dem Akteur des Tokens, sodass kein Zustand zwischen zwei Anfragen liegt. Erwogen wurde, JSON-RPC und Transport selbst umzusetzen; Aushandlung der Protokollversion, Batches, Benachrichtigungen und die Fehler des Transports nähme dann niemand ab.

## Consequences

- Ein MCP-Client authentifiziert sich mit einem API-Token im Header `Authorization`, nicht per OAuth, wie es die Autorisierung von MCP für öffentliche Server vorsieht. Ein Client, der nur OAuth kann, verbindet sich nicht; OAuth kommt, falls nötig, mit Identität und Zugriff.
- Ein Agent, der einen Tool-Aufruf ohne `idempotencyKey` wiederholt, führt die Mutation erneut aus; das Argument ist optional, wie der Header.
- Der Endpunkt prüft den Header `Origin` nicht, den die Spezifikation gegen DNS-Rebinding verlangt: Ein Browser schickt das Token nicht von selbst mit, weil die API keine Cookies kennt.
- Der Body einer Anfrage ist wie bei der HTTP-API höchstens 1 MiB groß; einen größeren lehnt der Transport mit 413 als Fehler von JSON-RPC ab.
- Die Liste der Tools ist die der Operationen der aktiven Plugins; sie meldet keine Änderung (`listChanged`), weil sich die Operationen erst mit einem Neustart ändern.
