# Events gehen über eine Outbox in Postgres, ein Event-Abo ist eine Capability je Event

Plugins sollen aufeinander reagieren, ohne einander zu importieren. Ein Plugin publiziert dafür Events aus seinen Mutationen, andere abonnieren sie. Ein Event darf nie von einer Mutation erzählen, die es nicht gibt, und nie verloren gehen, wenn es sie gibt.

`ctx.publish()` schreibt das Event deshalb in der Transaktion der Mutation nach `core.events`, die Outbox, und der Core stellt es erst nach dem Festschreiben zu. Ein Rollback nimmt das Event mit; ein Absturz nach dem Festschreiben lässt es in der Tabelle liegen. Erwogen wurde, Events nach dem Commit im Prozess an die Handler zu geben, ohne Tabelle; ein Absturz zwischen Commit und Aufruf verlöre das Event dann unbemerkt. Erwogen wurde auch `LISTEN`/`NOTIFY`; eine Notification erreicht nur, wer gerade zuhört, und ersetzt die Tabelle nicht.

Beim Publizieren entsteht in `core.event_deliveries` je eine Zustellung für jedes aktive Plugin, das das Event abonniert. Erwogen wurde ein Lesezeiger je abonnierendem Plugin über `core.events`; dann hielte ein Event, dessen Handler scheitert, alle folgenden dieses Plugins auf, oder der Zeiger bräuchte doch eine Liste der Ausnahmen. Eine Zeile je Zustellung trägt Versuche und nächsten Zeitpunkt für sich und lässt sich mit `FOR UPDATE SKIP LOCKED` sperren, sodass zwei Prozesse dieselbe Zustellung nicht zugleich versuchen.

Der Handler läuft in einer Transaktion mit dem Schema seines Plugins als `search_path`, und der Core vermerkt die gelungene Zustellung in derselben Transaktion. Was ein Handler in seine Datenbank schreibt, geschieht damit genau einmal, obwohl die Zustellung nur „mindestens einmal“ zusagt. Erwogen wurde, den Vermerk nach dem Handler in einer eigenen Transaktion zu schreiben; dann wiederholte ein Absturz dazwischen auch die Schreibzugriffe des Handlers, und jeder Handler müsste selbst dagegen vorsorgen. Wirkungen außerhalb der Datenbank bleiben „mindestens einmal“: Die ID des Events ändert sich bei einer Wiederholung nicht und dient als Idempotency-Key. Scheitert der Handler, rollt ein Savepoint zurück, was er geschrieben hat, und dieselbe Transaktion verschiebt die Zustellung.

Eine gescheiterte Zustellung wird ohne Obergrenze wiederholt, mit exponentiell wachsender Wartezeit und Full Jitter (Basis 1 s, höchstens 5 min). Erwogen wurde, nach einer festen Zahl von Versuchen aufzugeben; ohne Dead-Letter-Ablage, die mit den Jobs kommt (#10), wäre das Event dann still verloren. Die Frist eines Handlers ist `PLUGIN_HOOK_TIMEOUT_MS`, dieselbe wie für `activate` und `deactivate`; erwogen wurde eine eigene Variable, für die es noch keinen Anlass gibt.

Die Definition eines Events nennt sein Plugin (`plugin`, `name`, `version`, `payload`) und liegt im Contract des publizierenden Plugins (ADR-0004). Das publizierende Plugin führt sie in `definePlugin({ events })`, und `publish` nimmt nur ein dort geführtes Event des eigenen Plugins an. Ein abonnierendes Plugin kann die Definition nur aus dem Contract importieren, das sichern die Architekturtests; eine Definition außerhalb des Contracts kann deshalb niemand abonnieren. Erwogen wurde, den Namen des Plugins beim Publizieren aus der Operation abzuleiten statt ihn in die Definition zu schreiben; dann kennte ein Abo nur den halben Namen des Events. Ein Abo setzt kein `requires` voraus: Events sind die Richtung, in der ein Plugin auf eines reagiert, das seinerseits von ihm abhängt, und `requires` in beide Richtungen wäre ein Kreis.

Ein Event-Abo ist eine Capability je Event (`event:<plugin>.<Name>`), die das Manifest deklariert; ein Abo ohne sie ist ein Ladefehler (`invalid_manifest`). Erwogen wurde eine einzige Capability für alle Abos. Das Manifest sagte dann nur, dass ein Plugin überhaupt zuhört, nicht wem, und eine spätere Verschärfung bräche jedes Plugin, das sie deklariert. Von der Capability je Event lässt sich dagegen jederzeit zu einer gröberen lockern.

Die ID eines Events kommt aus einer eigenen Quelle der Pipeline (`newEventId`), wie die eines Audit-Eintrags (ADR-0014), damit ein publiziertes Event im Test-Harness die IDs der Operation nicht verschiebt.

## Consequences

- Die Reihenfolge der Zustellung ist nicht zugesichert. Der Core versucht fällige Zustellungen in der Reihenfolge, in der die Events geschrieben wurden, aber eine gescheiterte wird später nachgeholt. Ein Handler, der Reihenfolge braucht, liest den Stand beim publizierenden Plugin nach.
- Ein Plugin, das ein Event erst später abonniert oder beim Publizieren nicht aktiv war, erhält es nicht. Ein Read Model, das vollständig sein muss, braucht dann einen eigenen Abgleich.
- Eine Zustellung an ein Plugin, das nicht aktiv ist, bleibt ohne Frist liegen. `core.events` und `core.event_deliveries` wachsen mit jeder Mutation, die publiziert, und haben noch keine Aufbewahrungsfrist; sie folgt zusammen mit der des Audits.
- Das abonnierende Plugin prüft die Payload mit dem Schema der Definition, die es importiert hat. Ein Event entwickelt sich deshalb additiv; ein Feld zu entfernen ist ein neues Event oder eine neue Version nach Abstimmung mit allen, die es abonnieren.
- Ein Handler, der seine Frist überschreitet, läuft im Prozess weiter; der Core kann ihn nicht abbrechen. Seine Schreibzugriffe scheitern, sobald der Savepoint zurückgerollt ist.
- Ein Handler hat keinen Akteur und publiziert selbst keine Events. Beides kommt mit dem Plugin-Service-Account.
- Der Core publiziert noch keine eigenen Events (`WorkspaceDeleted`); `publish` einer Operation des Cores findet deshalb kein deklariertes Event.
- Ein Plugin mit Datenbankzugriff schreibt im selben Transaktionsobjekt wie der Core. Dass es die Outbox nicht selbst anfasst, sichern ADR-0003 und die Review, nicht Postgres.
