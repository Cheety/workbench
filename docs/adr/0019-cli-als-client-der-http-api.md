# Die CLI ist ein Client der HTTP-API einer laufenden Instanz, ihr Token kommt aus Umgebung oder Datei

Jede Operation ist per CLI aufrufbar (Story 25). Das Kommando `workbench` ist ein dünner Client der HTTP-API (ADR-0013): Es schickt `POST /api/workspaces/{workspace}/operations/{operation}` mit der Eingabe als Body und dem API-Token als Bearer-Token und gibt die Antwort wieder, die Ausgabe als JSON auf der Standardausgabe, Problem Details als lesbare Zeilen mit dem stabilen `code` auf der Standardfehlerausgabe. Die Pipeline, die Authentifizierung, die Prüfung der Eingabe gegen das Eingabe-Schema, Idempotency-Keys und Audit laufen damit genau einmal, in der Instanz, wie für HTTP und MCP.

Erwogen wurde, die Pipeline im Prozess der CLI aufzurufen, wie es `create-service-account` mit dem Schema `core` tut. Dann bräuchte die CLI die Datenbank-URL und damit mehr Rechte als jedes Token, müsste die Plugin-Pakete laden und aktivieren, deren `activate` ein zweites Mal liefe, und das Token gegen die Datenbank prüfen, statt es der Instanz zu überlassen; Events und Jobs einer Mutation weckten die Zustellung der Instanz nicht, sie warteten auf deren nächste Abfrage. Ein Nutzer im Terminal, für den Story 25 die CLI vorsieht, hat Zugang zur Instanz, nicht zu ihrer Datenbank. Erwogen wurde auch, die CLI als MCP-Client von `POST /api/mcp` zu bauen; dann käme jeder Aufruf über JSON-RPC und die Namen der Tools, und ein Fehler als Tool-Fehler mit Text, den die CLI erst wieder auspacken müsste, ohne dass sie etwas von MCP bräuchte.

Damit die CLI die Operationen einer Instanz listen kann, bietet die HTTP-API `GET /api/operations` an, mit Namen und Art jeder Operation der aktiven Plugins, authentifiziert wie jeder Aufruf und im OpenAPI-Vertrag als `listOperations` beschrieben. Erwogen wurde, die Liste aus `docs/openapi.json` zu lesen; der Vertrag beschreibt aber alle Plugin-Pakete des Repositorys, nicht die in einer Instanz aktiven, und läge nicht neben jeder CLI. Erwogen wurde auch `tools/list` des MCP-Endpunkts; dann hinge die CLI doch an MCP. Die Liste nennt die Eingabe-Schemas nicht: Sie stehen im OpenAPI-Vertrag, und was die API nicht verspricht, muss sie nicht halten.

Das CLI-Kommando einer Operation ist `<plugin> <operation in kebab-case>`, `reference.createNote` heißt `reference create-note`, wie Kommandos auf der Kommandozeile üblich gruppiert sind. Die Abbildung lässt sich umkehren, weil der Name einer Operation in camelCase (ADR-0010) keinen Bindestrich und ein Kommando in kebab-case keinen Großbuchstaben enthält; die CLI nimmt nur Kommandos in kebab-case an, sodass kein zweiter Name dieselbe Operation ruft (wie bei MCP, ADR-0018). Ein Kommando, das die Instanz nicht kennt, beantwortet die Instanz mit `unknown_operation`, ohne dass die CLI vorher die Liste holt. `operations` ist ein Wort, ein Aufruf immer zwei; ein Plugin namens `operations` verdeckt deshalb nichts. Die Eingabe kommt als JSON in `--input`, wie der Body der HTTP-API. Erwogen wurde, aus dem Eingabe-Schema eine Option je Feld abzuleiten (`--title Plan`); dafür bräuchte die CLI vor jedem Aufruf das Schema und eine Abbildung von Strings auf beliebige JSON-Typen, wie sie ADR-0013 für Query-Parameter verwarf. Die CLI prüft die Eingabe nicht selbst gegen das Schema, nur, dass sie JSON ist; die Pipeline prüft sie mit denselben Meldungen wie für HTTP und MCP, und ein zweiter Validator in der CLI wiche davon ab.

Das API-Token kommt aus `WORKBENCH_TOKEN` oder aus dem Feld `token` der Konfigurationsdatei (`WORKBENCH_CONFIG`, sonst `cli.json` unter `$XDG_CONFIG_HOME/workbench` oder `$HOME/.config/workbench`), die Umgebung geht vor, wie üblich für Werkzeuge, die in CI und im Terminal laufen. Eine Option `--token` gibt es nicht: Ein Argument steht in der Prozessliste jedes Nutzers des Rechners, in der Shell-History und in den Logs von CI-Systemen, die Kommandos ausgeben. Fehlt das Token oder ist die Konfiguration ungültig, nennt die CLI die Variable, das Feld oder die Datei, nie einen Wert. Erwogen wurde ein Kommando `login`, das das Token interaktiv abfragt und ablegt; es kommt, falls nötig, mit Identität und Zugriff, wenn Nutzer Tokens selbst anlegen.

## Consequences

- Die CLI braucht eine laufende, gestartete Instanz; vorher antwortet diese mit `instance_not_ready`, ohne sie meldet die CLI `cannot be reached`.
- Exit-Code 0 heißt gelungen, 1 gescheitert (Problem Details der Instanz, keine Antwort, eine fremde Antwort), 2 ungültiger Aufruf oder ungültige Konfiguration, bevor etwas die Instanz erreicht.
- Die CLI prüft die Rechte der Konfigurationsdatei nicht; wer sie für andere lesbar ablegt, gibt das Token preis.
- Eine Eingabe in `--input` steht in der Prozessliste; geheime Eingaben gehören nicht dorthin, solange die CLI keine Eingabe von der Standardeingabe liest.
